Penalty-deduction recovery for a 3PL

When a client deducts a penalty from a logistics company's payment, this service checks the deduction against that client's own agreement, the company's trip records and dated public evidence. It answers valid, disputable or cannot verify, with every fact sourced, and sends a dispute exactly once after a named person approves.

Technical architecture

Models read, code decides, people authorise

The verdict is computed by deterministic code from confirmed contract terms and cited records. A model can propose a term, a column mapping or a news passage, and every proposal is checked against the source text. Two points need a named person. Everything that costs money passes through one broker.

Restart is the same as re-run

Every stage result is stored under a hash of what it read. After a kill, a settings change or a new document, the same command runs again and only what changed is recomputed.

Nothing is paid for twice

A paid response is written to the cache and the ledger in one step, before it is used. Two deductions on the same route and dates share one search.

Nothing is sent twice

A letter's identity is fixed by its content. Sending records its intent first; on restart it checks the outbox by that identity before delivering.

Every citation is re-checked

Before a verdict becomes disputable, and again before a letter is sent, each clause, record and passage is verified against what is stored. The check can only downgrade.

Business architecture

Who pays whom, and where the service sits

The buyer is the logistics company's finance controller. Today the billing team writes most deductions off because each one takes hours to contest; large sums go to lawyers. The service is paid only when money comes back.

How to run

From a fresh clone

Python 3.11 or newer. Setting PDR_OFFLINE=1 guarantees nothing is sent to a paid provider; the arithmetic and records cases need no network at all.

git clone https://github.com/HarshLk/crustdata-hackathon.git && cd crustdata-hackathon
pip install -r requirements.txt
export PYTHONPATH=. PDR_OFFLINE=1 PDR_DATA_DIR="$PWD/demo-data"
alias pdr='python -m pdr.cli'

bash scripts/smoke.sh                     # one-command check; must end with SMOKE OK

pdr doctor && pdr init
pdr run --in tests/cases/case06_wrong_base_over_cap --out "$PDR_DATA_DIR/out"
pdr status                                # queue and stage table
pdr actions                               # letters waiting for approval
pdr approve '<action id>' --role kam --name "A. Manager"
pdr send && pdr outbox                    # sent exactly once
pdr ledger --by deduction && pdr economics
python -m pytest -q                       # full suite, offline

Open demo-data/out/index.html for the case file. After a kill, run the same command again: finished stages are reused and an unfinished send is completed once.

Limitations

What does not work yet

Each limit fails safe toward "cannot verify", never toward a wrong dispute.

  • No model key was tested. Clause reading, free-text parsing and passage reading ran on rule-based fallbacks.
  • Live news search can miss. About 80% of Crustdata news results are Google redirect links, and Google holds back fresh ones for a few minutes. In three live runs on 22 Nov the force-majeure case returned "cannot verify, no evidence found".
  • Offline, the 14 news-dependent cases return cannot verify from the command line. Their recorded responses are used only by the automated tests.
  • Sample agreements are stand-ins built from real public tender clauses, and flagged as such on every verdict.
  • The fee rate is not yet set.

Future work

What comes next

Built on branches, not yet merged

  • Decision log: a readable record of how each verdict was reached, shown on the case page
  • Model costs in the ledger, and support for other model providers with the user's own key
  • Alert outbox: "verdict ready" and "approval needed" messages, sent at most once

Planned

  • Case chat that answers only from the decision log and never decides
  • A live approval page beside the static case file
  • "Search deeper" on request: next page of results and every query variant
  • Real WhatsApp delivery for alerts

Source reliability

  • Ask Crustdata to return publisher links in news results; today about 80% are Google redirect links
  • Retry unresolved links a few minutes later within the same run
  • Official sources that need no search links: district orders, weather office releases, traffic police advisories

Before real use

  • Test clause reading and passage reading with a real model key; so far only rule-based fallbacks have run
  • Replace stand-in agreements with the client's signed ones
  • A second person's check of the route-places file
  • Late client documents check, and deletion of trip data after the retention period
